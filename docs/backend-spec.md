# Backend Specification

Spring Boot API in front of Supabase (Auth, Postgres). Decisions D1–D6 are in the [README](../README.md); the client side of sync is in [android-spec.md](android-spec.md) §8.

## 1. Responsibilities

| Component | Responsibility |
|---|---|
| **Supabase Auth** | Sign up, sign in (email/password, Google ID token), email confirmation, password reset, token refresh. Called directly by the Android app. |
| **Spring Boot API** | Validates Supabase JWTs; owns all activity data: validation, idempotent writes, delta sync, account deletion. |
| **Supabase Postgres** | Stores activities and track points. Reached only by the API. |

No map imagery is stored anywhere on the backend (D4); Supabase Storage is not used.

## 2. Stack

| Area | Choice |
|---|---|
| Runtime | Kotlin, current stable Spring Boot and Java LTS, Gradle |
| Web | Spring MVC, Jakarta Validation, RFC 9457 problem responses |
| Security | Spring Security OAuth2 resource server (JWT) |
| Data | Spring Data JPA, Flyway migrations, HikariCP |
| HTTP out | `RestClient` for the Supabase Auth Admin API |
| Ops | Actuator (health, metrics), structured JSON logs, Docker image |
| Tests | JUnit 5, Testcontainers (Postgres), MockMvc + `spring-security-test`, WireMock for outbound HTTP |

Package layout: `auth` (security config, current-user resolver), `activity` (controller, service, repository, DTOs), `account`, `common` (errors, cursor codec).

## 3. Supabase setup

1. **Auth:** enable Email (confirmation on) and Google providers. Google provider is configured with the web OAuth client id (plus the Android client id as an authorised client). Redirect URL allow-list contains `pulsefit://auth-callback`. JWT signing uses asymmetric keys so the API can verify via JWKS.
2. **Database:** all application tables live in schema `app`, which is **not** in PostgREST's exposed schemas. Row Level Security is enabled on every table with no policies, so even if the schema were exposed, the anon and authenticated roles could read nothing. The API connects with a dedicated role `pulsefit_api` that owns the tables.
3. **Connection:** use the Supabase pooler in **session mode** (prepared statements used by JPA do not work in transaction mode). Hikari pool max 10.
4. Two Supabase projects: `dev` and `prod`.

### Configuration (environment variables)

| Variable | Purpose |
|---|---|
| `SUPABASE_URL` | Project URL; issuer is `${SUPABASE_URL}/auth/v1`, JWKS at `${SUPABASE_URL}/auth/v1/.well-known/jwks.json` |
| `DB_URL`, `DB_USER`, `DB_PASSWORD` | Postgres via session pooler |
| `SUPABASE_SERVICE_KEY` | Secret key for Auth Admin calls (account deletion). Server only; never shipped in the app. |

## 4. Security

- Stateless; every `/v1/**` request needs `Authorization: Bearer <Supabase access token>`.
- Token validation: signature via JWKS (cached), issuer, expiry, audience `authenticated`. The user id is the `sub` claim (UUID).
- **Authorization rule:** every query is scoped by `user_id = sub`. A resource belonging to another user is reported as `404`, never `403`, so ids cannot be probed.
- A `profiles` row is created on a user's first authenticated request (just-in-time provisioning).
- Request limits: body ≤ 5 MB (after gzip decoding ≤ 20 MB), ≤ 50 000 points per activity. Rate limit: 120 requests/min per user (`429` with `Retry-After`).
- CORS disabled (no browser clients). HTTPS terminated by the host. No coordinates in logs.

## 5. Data model

```sql
create schema if not exists app;

create table app.profiles (
  id          uuid primary key,               -- = auth.users.id
  created_at  timestamptz not null default now()
);

create table app.activities (
  id                  uuid primary key,       -- generated by the client
  user_id             uuid not null references app.profiles(id) on delete cascade,
  type                text not null check (type in ('WALKING','RUNNING','INLINE_SKATING','CYCLING')),
  title               text not null check (char_length(title) between 1 and 80),
  started_at          timestamptz not null,
  ended_at            timestamptz not null check (ended_at >= started_at),
  zone_id             text not null,
  active_duration_ms  bigint not null check (active_duration_ms >= 0),
  elapsed_duration_ms bigint not null check (elapsed_duration_ms >= active_duration_ms),
  distance_m          double precision not null check (distance_m >= 0),
  avg_speed_mps       double precision not null check (avg_speed_mps >= 0),
  max_speed_mps       double precision not null check (max_speed_mps >= 0),
  elevation_gain_m    double precision,
  time_slow_ms        bigint not null default 0,
  time_average_ms     bigint not null default 0,
  time_high_ms        bigint not null default 0,
  source              text not null check (source in ('PHONE','WATCH')),
  preview_polylines   text[] not null,                    -- simplified track, one encoded polyline per segment
  version             bigint not null default 1,          -- +1 on every change
  created_at          timestamptz not null default now(),
  updated_at          timestamptz not null default now(), -- server clock, set on every change
  deleted_at          timestamptz                          -- tombstone
);
create index activities_sync_idx on app.activities (user_id, updated_at, id);
create index activities_list_idx on app.activities (user_id, started_at desc) where deleted_at is null;

create table app.track_points (
  activity_id uuid not null references app.activities(id) on delete cascade,
  seq         integer not null,
  segment     integer not null,
  lat         double precision not null check (lat between -90 and 90),
  lng         double precision not null check (lng between -180 and 180),
  altitude_m  double precision,
  speed_mps   real,
  accuracy_m  real not null,
  recorded_at timestamptz not null,
  primary key (activity_id, seq)
);

alter table app.profiles     enable row level security;
alter table app.activities   enable row level security;
alter table app.track_points enable row level security;
```

Notes:
- `updated_at` always comes from the database clock, so the delta cursor is monotonic regardless of device clocks.
- Deleting an activity sets `deleted_at`, bumps `version`/`updated_at`, and removes its track points. Tombstones are purged after 90 days by a scheduled job.
- Statistics are stored as sent by the client; the server validates ranges and consistency but does not recompute them.

## 6. REST API

Base path `/v1`. JSON, camelCase, timestamps ISO-8601 UTC. `Content-Encoding: gzip` accepted on requests.

| Method & path | Purpose | Success |
|---|---|---|
| `GET /v1/me` | Current user id and email (from token) | `200` |
| `DELETE /v1/me` | Delete account and all data | `204` |
| `PUT /v1/activities/{id}` | Create an activity with its points (idempotent) | `201` created, `200` already existed |
| `PATCH /v1/activities/{id}` | Change the title | `200` |
| `DELETE /v1/activities/{id}` | Soft-delete (idempotent) | `204` |
| `GET /v1/activities/{id}` | One activity (metadata) | `200` |
| `GET /v1/activities?cursor=&limit=` | Delta feed incl. tombstones | `200` |
| `GET /v1/activities/{id}/points` | Track points | `200` |
| `GET /actuator/health` | Liveness/readiness (unauthenticated) | `200` |

### 6.1 Create — `PUT /v1/activities/{id}`

```json
{
  "type": "RUNNING",
  "title": "Morning Run",
  "startedAt": "2026-11-16T06:30:00Z",
  "endedAt": "2026-11-16T07:05:12Z",
  "zoneId": "Europe/Prague",
  "activeDurationMs": 2010000,
  "elapsedDurationMs": 2112000,
  "distanceM": 5234.7,
  "avgSpeedMps": 2.60,
  "maxSpeedMps": 4.12,
  "elevationGainM": 41.0,
  "timeSlowMs": 310000, "timeAverageMs": 1400000, "timeHighMs": 300000,
  "source": "PHONE",
  "previewPolylines": ["_p~iF~ps|U_ulLnnqC_mqNvxq`@"],
  "points": [
    { "seq": 0, "segment": 0, "lat": 50.0875, "lng": 14.4213, "altitudeM": 201.3,
      "speedMps": 2.4, "accuracyM": 6.0, "time": "2026-11-16T06:30:02Z" }
  ]
}
```

Rules:
- `{id}` must be a UUID. If no row exists → insert activity and points in one transaction → `201`.
- If a row with this id already exists for this user → no change, return the stored representation → `200` (this is what makes retries safe). If it exists but is deleted → `410`. If it belongs to another user → `409` (id collision; client generates a new id).
- Validation (`422` with per-field errors): `seq` contiguous from 0; `recorded_at` non-decreasing; points within `[startedAt − 60 s, endedAt + 60 s]`; `segment` non-decreasing; at least 2 points; `zoneId` is a valid zone; `previewPolylines` has 1–50 entries that decode to valid coordinates, at most 100 points in total; limits from §4.

Response body (also used by `GET` and `PATCH`): all request fields except `points`, plus `id`, `version`, `updatedAt`, `deleted`.

### 6.2 Update title — `PATCH /v1/activities/{id}`

Request `{ "title": "Lunch run", "version": 3 }`. If `version` matches → update, `version + 1`, `200`. If not → `409` whose body contains the current representation. Deleted → `410`.

### 6.3 Delta feed — `GET /v1/activities`

`cursor` is opaque (base64 of `updated_at` + `id`); omitted on first sync. `limit` default 100, max 500.

```json
{
  "items": [ { "id": "…", "version": 4, "updatedAt": "…", "deleted": false, "…": "…" },
             { "id": "…", "version": 2, "updatedAt": "…", "deleted": true } ],
  "nextCursor": "MjAyNi0xMS0xNlQwNzoxMDowMC4xMjM0NTZafGFiYy4uLg",
  "hasMore": false
}
```

Ordered by `(updated_at, id)` ascending, strictly after the cursor. Tombstones carry only `id`, `version`, `updatedAt`, `deleted`. To avoid missing rows committed out of order, the feed only returns rows with `updated_at` older than 2 seconds.

### 6.4 Errors

`application/problem+json`:

```json
{ "type": "about:blank", "title": "Unprocessable Entity", "status": 422,
  "code": "VALIDATION_FAILED",
  "errors": [ { "field": "points[12].lat", "message": "must be between -90 and 90" } ] }
```

| Status | `code` | Meaning |
|---|---|---|
| 400 | `MALFORMED_REQUEST` | Unparseable body, bad UUID, bad cursor |
| 401 | `UNAUTHENTICATED` | Missing, invalid or expired token |
| 404 | `NOT_FOUND` | No such resource for this user |
| 409 | `VERSION_CONFLICT`, `ID_CONFLICT` | Stale version; id in use |
| 410 | `DELETED` | Activity was deleted |
| 413 | `PAYLOAD_TOO_LARGE` | Size limits exceeded |
| 422 | `VALIDATION_FAILED` | Field validation |
| 429 | `RATE_LIMITED` | Too many requests |

## 7. Map images (D4)

The backend neither stores nor renders map imagery. Clients draw maps on the device from track data. To let a client draw a thumbnail without downloading the full track, each activity carries `previewPolylines`: the track simplified on the device to at most 100 points, one Google encoded polyline per segment. The server validates and stores it as sent and returns it in every activity representation, including the delta feed.

## 8. Account deletion — `DELETE /v1/me`

In order: delete `app.profiles` row (cascades to activities and points) → delete the user through the Supabase Auth Admin API. Each step is idempotent; if the last step fails the endpoint returns `503` and the client may retry. Afterwards the user's tokens fail validation at next refresh; the API additionally rejects tokens whose `sub` has no profile and was deleted (deleted ids are kept in a small `app.deleted_users` table for 24 h to stop just-in-time re-provisioning from a still-valid access token).

## 9. Non-functional

- **Performance:** p95 < 300 ms for list/patch/delete; create with 10 000 points < 2 s (JDBC batch insert, `reWriteBatchedInserts=true`).
- **Observability:** request id in logs and in problem responses; metrics for request latency and sync payload sizes.
- **Migrations:** Flyway on startup; migrations are forward-only.
- **Deployment:** one Docker image, configuration by environment only; health probe on `/actuator/health/readiness`. CI: build → tests → image.

## 10. Test matrix

| Area | Cases |
|---|---|
| Security | No token → 401; expired → 401; wrong issuer/audience → 401; valid → 200; user A cannot read, patch, delete or fetch points of user B (404) |
| Create | 201 then identical retry 200 with one row and no duplicate points; each validation rule → 422; over limits → 413; create after delete → 410 |
| Patch | Success bumps version; stale version → 409 with current body; deleted → 410 |
| Delete | 204, repeat 204; points removed; tombstone appears in feed |
| Feed | Paging with `limit`; cursor stability under concurrent writes; includes updates and tombstones exactly once; other users' rows never appear |
| Preview | `previewPolylines` round-trips unchanged through create, get and feed; undecodable or over-limit value → 422 |
| Account | After delete: no rows, Auth Admin called; old token rejected |
